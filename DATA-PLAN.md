## Long-term data behavior
- **Refresh policy**: none — no cron; state changes only through the user's taps/edits in the artifact, plus the one-time idempotent seedInitial import (same exact rows Eddie handed over for the original app) run once post-submit; it no-ops when rows already exist
- **Growth**: one row per task per day, templates, habit definitions and per-day habit logs; nothing auto-deletes user rows
- **Ordering**: single combined todo list per day — carried-over tasks first, then the day's tasks, timed items first within each group; carried-over tasks appear inline with the todos (no separate section)
- **"Next day" tag (renamed from "carried over", 2026-10-27)**: Eddie's reference format is a dark pill with a butter-yellow outline and butter-yellow lowercase text. The tag no longer appears on the live copy of a carried task: on today's page (and any later day it is carried to) the task looks exactly like any other task, with no tag. The tag appears only on the copy shown on the day the task was added, once that day is in the past and the task wasn't finished on that day itself — that copy is greyed out, its toggle is disabled, and it has no ⋮ menu (non-interactive). Whether a task finished on its added day is decided from `tasks.done_day` (now returned by getDay as `doneDay`; pre-existing rows fall back to the UTC date of `done_at`, same fallback the server already used). Moved-on copies are excluded from their added day's progress count, since they can never be checked off there. The user-visible label is "next day" everywhere; the internal API field name `carried` is unchanged.
- **Checked-off carried tasks (bug fix, 2026-10-27)**: Eddie reported that checking off two tasks from today made them disappear. Cause: `getDay` returned carried-over tasks only when `done = 0`, and same-day tasks only when `day = viewed date`, so a carried task ticked done fell out of both lists (it was saved as done in the DB, just never shown again). Fix: `tasks.done_day` (migration 0003, backfilled from `done_at`) records the day view a task was checked off from — `toggleTask` now accepts an optional `viewDate` the client passes as the selected date — and `getDay` keeps a finished carried task on the list for exactly that day (visible, crossed off, counted in progress); on later days it no longer appears. Rows finished before the fix fall back to the UTC date of `done_at`.
- **Time semantics**: days are plain local YYYY-MM-DD dates; AM/PM reminder slots are display labels (9:00 AM / 4:30 PM), not scheduled notifications
- **Back-to-today spacing and direction (2026-10-27)**: the gap between the "Back to today" link and the LOGS section was tightened (`.back-today` margin/padding and `.section-head` top margin reduced). The link also shows direction: "Back to today >>" when the viewed day is before today (today is forward), "<< Back to today" when the viewed day is after today (today is backward).
- **Tags replace notes (2026-10-27)**: Eddie asked for the New Task page to have a title and tags only — notes are gone entirely. Tags live in a new `tasks.tags` column (migration 0004) as a JSON array of labels. In the form, tags are typed into one field and separated by the Enter key only (Eddie simplified this on 2026-10-27 — commas no longer separate tags) — pressing Enter turns the typed text into a tag chip (Enter does not submit the form); chips can be removed with their ×, and any text still in the field when the confirm button is tapped is flushed in as a final tag too. The form's tag chips use the exact same style as the tags displayed on task rows (same solid dark fill, butter outline and text, size and padding). The old top-right ✓ ("yes") button moved to the bottom right of the pop-up as a dark pill button in the style of the Reminders pop-up's "+ Add" (labelled "+ Add" for a new task, "✓ Save" when editing), and the old generic X was replaced by the custom green X image (`close-x.png`) used on the Reminders pop-up. On task rows, tags render as pills in the same format as the "next day" tag (dark pill, butter-yellow outline and lowercase butter text, solid dark fill) in the row position notes used to occupy; notes are no longer displayed anywhere, `addTask` no longer accepts a note, and editing a task clears any legacy note still stored on it. The `note` column itself remains in the DB (and on templates) for backward compatibility but the task UI neither writes nor reads it.

- **One-time reminder display + next-day tasks checkable from their added day (2026-10-27)**: Eddie asked for two things. (1) A one-time reminder should display in the day's REMINDERS card on the date it is set for, with a different icon before it. Server check: `templateMatches` already matched `kind='once'` templates only on their `specific_date`, and `getDay`'s `recurringToday` already included them — but in the day card their icon was a faint paper-plane glyph that read much like the repeating circular arrow at 14px, they carried a leftover "SENT" label, and the Reminders manager pop-up filtered one-time reminders out of its list entirely (`kind !== "once"`), so a scheduled one-time reminder was invisible and unmanageable there. Fix (client only): one-time reminders in the day card now use a new calendar-with-marked-day icon (`OneTimeIcon`) on a solid butter-yellow disc (`.reminder-ic.once`), clearly apart from the repeating arrow on its sage disc, and show their time hint (e.g. "9:00 AM") instead of "SENT"; the manager pop-up now lists one-time reminders in their own "ONE-TIME" section with the same calendar icon, their set date via `shortWhen`, and the usual active switch + delete controls. (2) Tasks that moved on to the next day used to be locked on the day they were added (checkbox disabled, no interaction). Eddie wants them still checkable from that creation day — e.g. he actually finished one that day but forgot to tick it — so checking it there removes it from the carried-over data. The server already supported this (`toggleTask` records `done_day` from the passed `viewDate`; a task finished on its added day drops out of later days' carried lists), so the fix is client-side: an unchecked "next day" copy's paw button and body are no longer disabled and toggle normally, still rendered a bit greyed out (`.task.next-day` dimming kept) while unchecked; once ticked from its added day, `doneDay === day` makes `isNextDayCopy` false, so the copy returns to normal opacity with the tag gone and counts as a normal done task on that day. A next-day copy that was already checked off on a later day stays locked (`toggleLocked = nextDay && done`), so tapping it on the added day can't undo that later completion. The ⋮ menu remains hidden on next-day copies — the live copy on the later day is the one that gets edited/moved/deleted.

- **Check-off from tomorrow vanishing (bug fix, 2026-10-27, semantics clarified by Eddie same day)**: Eddie reported "Chat with Kaku" (a rolled-over task shown on both today and tomorrow) disappeared when he checked it off from tomorrow's page. Eddie's clarified model: a rolled-over task DOES belong on future pages, still open; checking it off on a future day keeps it crossed off on that page like any completed task, and on its original date the copy is greyed out and uninteractive; ONLY checking it off on the original page (even after that day has passed) makes the rollover disappear from future pages, no matter which date it rolled over to or was manually moved to. Reproduced against the actions with a probe task dated the day before: `getDay` kept a finished carried task only on its exact `done_day`, so a completion recorded from tomorrow (done_day = tomorrow) erased the task from today's rollover list even though it had rolled over there too. Fix (`getDay` only): a finished carried task now has a lifespan — it stays visible, crossed off, on every rollover day after its own date up to and including its done day (`done_day >= viewed date` instead of `done_day == viewed date`). Unfinished carried tasks are unchanged (returned on every later day, future included), and `toggleTask` still records the viewed day as `done_day` verbatim, future dates included — a future-page check-off is a real completion belonging to that page. Checking off on the original date sets done_day = the task's own day, so no later day falls inside the lifespan: the rollover disappears from all future pages and the original page shows a normal done task (the client's existing "next day" greyed/locked styling already keys off exactly this: greyed + tag while unchecked or finished later, locked once finished later, normal once finished on its own day). An earlier draft of this fix wrongly hid open carried tasks from future views and clamped future done days back to today; Eddie's clarification rejected both, and they were reverted before shipping.

- **Rollover semantics, final model + origin_day (2026-10-27)**: Eddie restated the rule after "Chat with Kaku" vanished when checked off from tomorrow's page: (1) a rolled-over task checked off on a future day stays on that page, crossed like any other completed task; (2) on its original date the copy is greyed out and uninteractive; (3) ONLY checking it off on the original page (even after that day has passed) makes the rollover disappear from future pages — no matter which date it rolled over to or was manually moved to. Two gaps in the previous build broke this: the client's `isNextDayCopy` required the origin day to be before today, so a task added today and checked off from tomorrow rendered as a normal, tappable done task on today's page instead of greyed + locked; and `moveTaskToDay` overwrote `tasks.day`, destroying the origin page's copy entirely, so after a manual move there was no original page left to check the task off on (and the server had no rule that an origin-day check-off clears a native future copy). Fix: new nullable `tasks.origin_day` column (migration 0005; null falls back to `day`), returned by `getDay` as `originDay`. `moveTaskToDay` now stamps `origin_day` (first move only) and changes only `day`. `getDay` was rewritten around origin O / live day S / done day D: V == O always returns the origin copy; open tasks show live on S and roll over past it (days between O and S after a manual move show nothing); tasks finished later (D > O) stay crossed on live days S..D; tasks finished on O (D == O) appear on no future page at all. The client's `isNextDayCopy` now keys on `selectedDate === originDay` and treats the copy as moved on when the task was manually moved (`day > originDay`), its day has passed, or it was checked off on a later day — the third condition is what greys + locks today's own copy after a tomorrow check-off. Unchecked origin copies remain interactive (greyed) per Eddie's earlier instruction; `toggleLocked = nextDay && done` locks them only once finished on a later day.

- **Week arrows step one day, slightly bigger (2026-10-27)**: Eddie asked for the two triangle arrows on the week strip to be just very slightly bigger, and for them to move the selected date left/right by one day instead of jumping a whole week. When the move crosses the end/beginning of the week it should switch to the next/prev week with the selected day at the first/last position in line. Implementation (client only): the arrows now call `shiftKey(d, -1)` / `shiftKey(d, 1)` (was ±7) and their aria-labels are "Previous day" / "Next day". Because the displayed week is derived from `weekStartKey(selectedDate)`, stepping off Saturday lands on the Sunday that starts the next week (first position) and stepping off Sunday lands on the Saturday that ends the previous week (last position) with no extra logic. Size: the triangle SVG grew from 13×18px to 15×21px and its button from 26px to 28px wide — a slight increase only.

- **Task ⋮ pop-up as a horizontal icon bar (2026-10-27)**: Eddie supplied a reference screenshot (`workspace/user/media_library/image/37/377d32d27def35ac8b93b01f42056ca98fc96918ef36a1f7c2e92a8caaa95488.jpg`) for the "more" (⋮) pop-up's UI: a horizontal capsule bar of icon-only actions hanging off the bottom-right of the task row, with a small pointer up to the ⋮ button. He asked to ignore the reference's style and use this app's own, to give the icons less space between them than the reference, and for the ⋮ icon itself to have no border with its style unchanged. Implementation (client only): `.task-pop` is now a cream (`--sheet-white`) capsule with a rotated-square pointer at its top right, holding stroke-style icons in the app's palette (dark ink for calendar/edit, `#a8324a` danger for trash) at a tight 2px gap between 36px round buttons — far tighter than the reference's wide spread. Actions are unchanged: calendar = Move to next day, pencil = Edit, trash = Delete (first tap arms it into a solid red "Delete?" pill, second tap deletes, as before); carried tasks get a fourth calendar-with-check icon for Move to this day. Buttons are icon-only with the old text labels kept as `aria-label`/`title`. `.task-menu` (the ⋮ button) was not touched — it remains borderless (`background: none; border: none`) in its existing style.
